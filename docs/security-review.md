The raw, unauthenticated [ZAP HTML](security-evidence/zap-2026-10-09/report.html), [JSON](security-evidence/zap-2026-10-09/report.json), and [scan configuration](security-evidence/zap-2026-10-09/zap.yaml), plus a [SonarQube Cloud API snapshot](security-evidence/sonar-2026-10-09.json), are committed for review. ## Findings and limits

The remaining Sonar vulnerability is rule `docker:S6471`: the official Caddy image runs as root in the edge container. This is a real privilege tradeoff because Caddy binds ports 80/443 and writes certificate data to named volumes. The container has no host filesystem or Docker socket mount, but a container compromise could still affect the gateway and its certificate material. Moving it to a non-root user requires a tested volume-ownership and port-binding migration; that change was not rushed into this short-lived demo.

The repeat ZAP report's informational alerts are a suspicious-comments match in a minified JavaScript bundle, identification of the site as a modern web app, and two cache observations on public content. The JavaScript evidence does not contain a secret. The cache observations did not target authenticated API responses; the gateway sets `no-store` on `/api/*`.

ZAP used a short, unauthenticated passive scan. It did not exercise signed-in task routes, authorization bypasses, or destructive attack techniques. Account ownership and CSRF behavior are covered by automated API, PostgreSQL, and browser tests. Off-host database backup and a restore drill remain outside this temporary assessment deployment.

## Password and credential storage

- User passwords are stored as Argon2id hashes, and session tokens are hashed before database storage. The browser receives a secure, HttpOnly cookie; authenticated writes use a CSRF token.
- The current Git tree tracks example environment files only. Real local `.env` and `apps/backend/.env` files are ignored; `setup:local` creates a random local database password and enforces owner-only (`600`) permissions on both files. A development-only database password appeared in earlier Git history and was removed. Never reuse that value for this host or another service.
- The EC2 database password belongs in `/etc/opt/foci-todo/production.env`, outside the checkout. The host check on October 9 returned `600 root:root /etc/opt/foci-todo/production.env`, confirming owner-only file access without displaying the value. The deployment command reads it on the host; no database password or long-lived AWS key is a GitHub Actions variable. Password uniqueness has not been independently verified. To recheck permissions without displaying the secret, run `sudo stat -c '%a %U:%G %n' /etc/opt/foci-todo/production.env` on EC2.
- Docker Compose passes the database password to containers as environment data. Host root users and Docker administrators can inspect it; `600` protects against ordinary local accounts, not those administrators. For a long-lived deployment, use managed secret storage and rotation, and test database backup and restore.
